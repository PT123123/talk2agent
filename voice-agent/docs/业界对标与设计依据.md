## 一、打断后的上下文同步（Context Desync）

### 业界共识

这是本次对标中**最重要的一条**，也是我们此前遗漏的。

问题：TTS 合成速度远快于播放速度。用户打断时，模型往往已经生成了完整回答。
如果直接把完整文本写进对话历史，下一轮模型会**以为那些没播出来的内容也说过**，
于是：

- 跳过用户其实没听到的解释
- 说"正如我刚才说的……"而用户压根没听到
- 下一轮基于错误前提推理

OpenAI 开发者社区把它列为该 API 上**最普遍的第一个生产 bug**：
> "are we really meant to delete the entire response text, or just what had not been
> heard by the client?" —— 答案是后者，且这需要客户端自行追踪状态，API 无法推断。

### 我们的实现

`src/orchestrator/interruption_truncation.hpp` + `AudioRouter` 播放进度追踪。

关键点：`AudioRouter` 区分**已推送**（pushed）与**已播放**（played）两个计数。
业界文档明确警告过：
> "the played-duration figure must come from real playback tracking
> (received or scheduled audio **overstates** it)"

我们把计数点放在 `get_playback_frames()` 里 —— 那是真正把采样交给声卡的地方。

打断时（`Orchestrator::sync_interrupted_context_`）：

1. 在 `stop_playback()` **之前**取 `played_ratio()`（之后缓冲被清，取不到）
2. 按比例截断，切点对齐最近句边界（避免半个句子）
3. 把"实际播出的"记入 `ContextManager`
4. 构造"被打断"说明写进 P2 层 —— 对应 Azure 的 `appended_text_after_truncation`，
   让模型知道为什么自己话没说完

### 与 Azure 的差异

Azure 的 `appended_text_after_truncation` 对 `server_vad` 不支持，
只支持语义 VAD 模式。我们用比例截断而非 VAD 类型判断，因此不依赖服务端能力。

## 二、语义轮次判定（Semantic Turn Detection）

### 业界共识

静音时长是**代理指标**，不是目标。纯时长阈值同时有两个失败方向：

| 场景 | 纯时长表现 |
|---|---|
| "我想问一下…（停 600ms）…那个项目" | **抢话**（把停顿当结束） |
| "好的" | **慢半拍**（等太久） |

LiveKit 的做法是用 135M 文本模型读最近几轮，预测"轮次是否完成"，
动态延长 VAD 静音窗口（宣称 -85% 意外打断，~50ms 推理）。
Pipecat Smart Turn 改用波形打分（ONNX CPU）。两者都是**模型**方案。

### 我们的选择：先建通路，用规则实现

`src/orchestrator/semantic_turn.hpp`

**为什么不用模型**：
- 引入 135M ONNX 模型会带来 ~50ms 推理 + 模型下载 + 跨语言验证成本
- 而我们的目标是先把"语义参与判断"这条**通路**建起来，接口稳定后再换实现

`CompletionHint` 三态 + `Eagerness` 三档，接口与 LiveKit/Pipecat 的模型
可替换点对齐 —— 换实现不改调用方。

`Eagerness` 的超时值直接对齐 OpenAI 官方（low=8s / medium=4s / high=2s）：

```cpp
Low:    { min_wait 500ms, max_wait 8000ms, doubt_bonus 1500ms }
Medium: { min_wait 350ms, max_wait 4000ms, doubt_bonus  800ms }
High:   { min_wait 200ms, max_wait 2000ms, doubt_bonus  300ms }
```

**默认 Low，因为中文需要**。依据来自 Qwen Realtime 评测与 Zylos 的观察：
> "Teams serving Chinese users report biasing toward low eagerness …
> anything above low eagerness split long sentences."

中文是"话题在前、评论在后"的结构，决定性信息常在句末
（"这个方案的**优点**是…"），Medium 会在中途插话。

### 我们的实现只"延长等待"不"缩短"

`on_eou_()` 里语义判定的作用是：**把 EOUDetector 的 force_ms 临时拉长**
（900ms → 8000ms），而不是"否决这一轮"。

原因：EOUDetector 是纯时长驱动的状态机，没有"延后再判定"的 API。
否决会导致文本需要从 `accumulated_text_` 取回（状态回滚），
而这条路径在 VAD 重新触发时容易出竞态。**只延长阈值是零风险的** ——
用户继续说话会自然走 VAD 流程，用户彻底停顿时 max_wait 兜底让出。

## 三、抢答（Fast Response / Ack）

### 业界依据

AWS 中国博客在延迟优化建议里明确列出：
> "执行长时间函数调用之前，输出提示信息，例如'处理中，请稍后…'，
> 从而减少客户的等待时间。"

这正是我们 `FastResponseLayer` 的做法。我们的额外设计是**阈值自适应**：
用每类任务的 EWMA 滑动均值而非硬编码 700ms，因为本地模型（几百 ms）
与在线 API（几秒）差异极大，固定值在任何一边都是错的。

与业界的差异：AWS 建议的是固定话术；我们用 `ProgressUtterancePolicy`
按 task_type 轮换候选话术。理由是每次都说同一句就是机器味的主要来源。

## 四、延迟预算

对标 production-voice-agents 给出的 800ms 预算表，映射到我们的实现：

| 阶段 | 业界典型 | 我们的实现 | 观测点 |
|---|---|---|---|
| 采集 + AEC | 20–40ms | 10ms 帧 + NLMS AEC | `speech_to_asr` |
| VAD + 轮次判定 | 200–400ms | Silero + EOU 双阈值 + 语义复核 | `eou_delay` |
| ASR | 100–500ms | Whisper / Paraformer | `speech_to_asr` |
| LLM TTFT | 300–500ms | 本地 GGUF / 在线 OpenAI 兼容 | `llm_ttft` |
| TTS 首音频 | 100–450ms | Kokoro / SAPI | `tts_first_audio` |
| 播放渲染 | 50–100ms | AudioRouter | — |
| **端到端** | **~800ms** | | `asr_to_first_audio` 是体感最关键的一条 |

我们把 `asr_to_first_audio` 单独列为指标并设 2000ms 预算，
因为它是用户体感的决定项（VAD/EOU 与 TTFT 占预算大头，符合业界分布）。

## 五、明确未采纳 / 未实现

| 项 | 业界做法 | 我们的状态 | 原因 |
|---|---|---|---|
| 语义 VAD 模型 | LiveKit 135M / Pipecat Smart Turn v3 | 规则版，接口已留 | 需要模型下载与跨语言验证；先建通路 |
| 端到端语音模型 | Nova Sonic / Qwen-Audio Realtime | 未做 | 架构上是 Pipeline；切换会绕过我们这整层 Runtime |

| 说话人分离 | Krisp / Qwen 声纹锁定 | 未做 | 单人场景优先级低 |
| 打断恢复评测 | IHBench | 未做 | 需要真人打断数据集 |
| 音频前置降噪 | Krisp（强调大量失败是音频问题） | AEC 已有，降噪无 | 当前麦克风环境尚可 |

## 六、调参依据

改动任何数值前先看这里，不要凭感觉：

| 参数 | 现值 | 依据 |
|---|---|---|
| `barge_in_min_ms` | 160 | 项目实施计划的硬指标；<160ms 视为语气词 |
| `eou_force_ms` | 900 | 千问 Qwen3-ASR 官方默认 800ms；对话场景推荐 400ms |
| 语义 `eagerness` | Low | 中文场景（Zylos/Qwen 评测） |
| `ack_threshold_ms` | 700（EWMA 自适应） | 本地 vs 在线差异过大，不可硬编码 |
| 抢答上限 | 1 句/轮 | 超过就像话痨 |
| BackgroundCache TTL | 1800s | 超过半小时的搜索结果过期会误导 |
| ContextManager 总预算 | 4000 字符 | 约等于 2000 token，给 LLM 留足系统提示空间 |

### 语言相关的已知偏差

- **中文 vs 英文的 EOU 阈值应该不同**。中文语速快（约 4-6 字/秒），
  同样的 900ms 静音在中文里间隔更短。当前未做语言自适应。
- **`looks_like_freshness_query` 的"最近"歧义**已在 R4 修复
  （情感倾诉误判），但类似的中文歧义词仍可能存在。
- Whisper tiny 对中文精度有限（M0 阶段已记录），影响所有下游判断的输入质量。
