# 按键打断与播报控制设计

> 状态：阶段 1 已落地，阶段 3 部分落地，阶段 2/4 未开始（2026-10-10 更新）
> 范围：本地语音输入期间如何控制 Agent 的流式文本播报（TTS），以及如何区分停止生成、暂停播报和静音。
> 目标：在已有本地 ASR/VAD/流式 TTS 的基础上，定义一套可逐步落地、用户可预测的操作语义。
>
> **实现现状见文末 §16**，下面各节是原始设计，描述的是"应该怎么做"。

## 1. 背景与目标

talk2agent 已经有按住空格说话的输入交互，也有 LLM 流式输出按句送入 TTS 的链路。下一步想达到的体验是：Agent 正在说话时，用户可以自然地插入一句话；播放停止后，麦克风继续采集，松开按键或检测到说完后提交语音；系统再根据实际播放进度和用户的新话语继续对话。

设计还需要明确区分三种意图：

1. **打断并接管话轮**：停止当前语音输出，必要时停止当前生成，开始/继续采集用户语音，并基于新语音启动一轮。
2. **暂停/静音输出**：用户暂时不想听，但不一定要取消模型生成；恢复后可继续播报，或者只恢复后续内容。
3. **关闭自动语音播报**：后续回答只显示文字，不自动发声；这通常是偏好设置，不等同于当前回答的暂停。

本文只做方案定义，不改变现有行为，也不承诺当前音频采集与播放已经具备可靠的全双工能力。

## 2. 当前代码基线

### 已有能力

| 能力 | 当前实现 | 说明 |
|---|---|---|
| 按住空格说话 | `src/gui/main_window.cpp` 的全局事件过滤器 | 按下开始语音，松开停止/结束输入；空格自动重复会被忽略。VAD 模式和 VAD 关闭模式分别走控制器的开始/停止接口。 |
| 流式文本转 TTS | `src/tts/streaming_speaker.hpp/.cpp` | 按句积累文本并交给独立线程合成/播放，可降低首句等待。 |
| 停止当前播报 | `StreamingSpeaker::stop()`、`TTSSpeaker::stop()`、TTS/SAPI stop 接口 | 流式 speaker 会停止播放、清除待播队列并请求简单引擎停止。 |
| 对转写文本进行轮次准入 | `src/orchestrator/turn_admission.cpp` | 按 backchannel、continuation、interruption、topic change 等意图决定是否起新轮、是否打断。 |
| 语音时长门槛 | `src/orchestrator/smart_turn.hpp/.cpp` | 已有最短语音时长、较长语音让出话轮、语义一致性阈值等逻辑。 |
| 级联取消基础设施 | `src/core/cancel_token.hpp`、Orchestrator | 当前轮取消令牌可用于协同停止 LLM、TTS 等工作。 |
| 中断上下文截断 | `src/orchestrator/interruption_truncation.hpp` 及 `docs/业界对标与设计依据.md` | 设计/实现了按实际播放进度截断未听到的回答内容，避免后续对话把未播内容当作已说内容。 |

### 重要差距与限制

- 空格目前是**语音输入的按住说话键**，不是专用的“打断 Agent”键。按键本身和 TTS 取消、生成取消、音频播放游标同步之间没有形成单一明确的用户操作契约。
- `TurnAdmission` 的入口是识别后的文本。若等到 ASR 完成再停止 TTS，用户可能要等一段时间；若在 VAD 起始就停止，则可能把咳嗽、附和或误触当成打断。
- `SmartTurn::evaluate_barge_in()` 是基于语音时长与 coherence 的判定逻辑，不等于“按键按下立即打断”。尤其 `[barge_in_min_ms, backchannel_max_ms]` 内的行为还依赖语义一致性。
- `StreamingSpeaker::stop()` 是停止并清队列的终止动作，不是可恢复的暂停/静音接口。停止后应视为本次播报作废；继续播放需要上层重新安排。
- 暂停当前音频输出与暂停模型生成是两个不同控制面。即使音频能暂停，LLM 可能继续生成并把更多文本放入队列；如果没有背压/队列策略，恢复时会出现陈旧内容积压。
- 播放期间可靠地采集用户声音需要处理扬声器回声、VAD/ASR 对播放回声的误识别和设备缓冲延迟。按键能定义意图，却不能替代 AEC、播放进度追踪或音频线程协调。
- 本地模型生成取消、TTS 合成取消、播放队列清理、已写入声卡缓冲的处理时延并不完全相同。已经发给设备的少量音频无法撤回，需要用小缓冲或淡出来降低尾音。

因此“本地语音输入已经完整”指输入侧已有可复用流程；仍需把输入控制与正在输出的 TTS/LLM 生命周期接起来，并验证播放期间的采集质量。

## 3. 术语和状态

| 名称 | 含义 | 典型动作 |
|---|---|---|
| 自动播报关闭 | 后续回答不自动送入 TTS；文字回答仍正常生成和显示 | 关闭“语音播报”偏好 |
| 静音 | 输出音量临时为 0，模型和 TTS 可继续工作 | 恢复音量后继续听当前输出（具体是否补播由策略决定） |
| 暂停 | 保留当前播放位置与可恢复缓冲，不继续向扬声器播放 | 恢复时从暂停位置继续 |
| 停止播报 | 清掉当前播放和未播放的合成/排队音频；模型可以继续生成 | 当前声音被丢弃，文字仍可完整显示 |
| 取消回答 | 取消当前轮的 LLM/工具/TTS 工作；清理尚未播放内容 | 这一轮不再继续，随后可开始新轮 |
| 打断并接管 | 一次用户动作触发停止/取消策略并采集用户语音 | 新语音成为下一轮输入 |
| barge-in 门槛 | 决定用户输入到什么程度才实际停止 Agent 输出 | 按键、时长、转写文本量、端点/语义等组合 |

术语要在 UI 与日志里保持一致。避免一个“静音”按钮有时只关音量、有时又取消回答。

## 4. 交互方案

### 方案 A：按下立即打断（建议作为第一版）

**操作**：Agent 播报时按住专用打断键；按下瞬间停止当前音频并取消当前回答，按住期间采集语音；松开结束录音并提交识别。

**优点**：因果关系清楚、停止延迟低、不会让 TTS 继续覆盖用户声音；按键本身就是明确的打断意图，较少依赖 ASR 猜测。

**代价**：按错会停止回答；需为“打断并说话”和普通 PTT 的按键冲突定义优先级。取消回答意味着未生成完的解释不会自动续播。

### 方案 B：按下先采集，达到门槛再打断

**操作**：按键后先启动采集。Agent 暂时继续播报；当语音持续达到阈值、partial transcript 达到字符/词数阈值，或者用户松开并形成完整 utterance 时，再停止/取消 Agent。

**优点**：能够过滤短促误触、咳嗽、短附和；符合“说几个字后再打断”的设想。

**代价**：门槛期间 Agent 声音可能污染识别；如果等 ASR 文本，一般比纯按键/VAD 动作更慢；用户说得越短，越可能无法及时停止对方。

**设计建议**：按键模式下，按键本身已是明确意图，可默认把停止时机设在 key-down；如果要延迟确认，应作为显式可配置的“确认后打断”策略，而非默认。延迟策略可在门槛期间将 Agent 音量压低或暂时 duck，而不是让双方保持同等音量。

### 方案 C：两个按键分工

推荐预留两个独立动作：

| 操作 | 推荐语义 | 是否取消生成 | 是否接收用户语音 |
|---|---|---:|---:|
| 按住“说话/打断”键 | 停止当前输出并开始 PTT；松开提交 | 默认是 | 是 |
| “暂停/恢复播报”键 | 暂停当前 TTS，重复按键恢复 | 否 | 否（除非同时开启语音输入） |
| 独立“停止回答”键（可选） | 取消当前轮，不启动麦克风 | 是 | 否 |

初版可以用一个 PTT 打断键加 UI 中的暂停/恢复按钮，避免一开始就引入多个全局快捷键的配置负担。

### 方案 D：只静音，不暂停/取消

把输出音量设为 0，文本生成和播放进度仍然前进。恢复后不重播静音期间的音频。这适合“我知道你还在讲，但暂时不需要声音”，不适合用户插话，因为它不自动开始采集，也不保证停止生成。

## 5. 推荐的第一版操作契约

建议初版约定如下：

1. **现有空格 PTT 保持原语义**：按下开始采集，松开结束采集；当 Agent 正在播报时，将这次明确的 PTT 按下作为“打断并接管”。
2. **key-down 时立即停止音频输出并取消当前回答**：取消令牌向 LLM/工具/TTS 传播，TTS pending 队列清空；播放进度先取样、再清缓冲。
3. **按住期间继续采集麦克风**：结束采集时走现有 VAD/ASR 流程，不因打断而丢掉用户 utterance。
4. **松开后正常做轮次准入**：识别文本进入 `TurnAdmission`，按正常策略判断是否启动新回答。手动打断只表示旧回答让出话轮，不应绕过 ASR 错误、空文本、取消或拒答等规则。
5. **新一轮回答仍受“语音播报”偏好控制**：关闭自动播报时，回答照常显示但不自动发声。
6. **独立的暂停/恢复控制不取消生成**：暂停期间定义 TTS/LLM 队列上限；超限后优先暂停 LLM 输出或丢弃尚未合成内容，避免恢复时播出过期长队列。
7. **停播状态要可见**：至少区分“正在听你说”“回答已停止”“播报已暂停”“自动播报关闭”。

这是建议的交互默认值，不是代码已经实现的行为。

## 6. 按键状态机

```text
IDLE
  ├─ PTT key-down ───────────────► CAPTURING
  ├─ pause key ──────────────────► PAUSED_OUTPUT（若正在播报）
  └─ mute toggle ────────────────► MUTED（输出策略开关）

AGENT_SPEAKING
  ├─ PTT key-down ───────────────► INTERRUPTING ─► CAPTURING
  ├─ pause key ──────────────────► PAUSED_OUTPUT
  ├─ stop key / Stop button ─────► CANCELLED（不自动开麦）
  └─ mute toggle ────────────────► AGENT_SPEAKING_MUTED

CAPTURING
  ├─ PTT key-up ─────────────────► TRANSCRIBING / WAIT_EOU
  ├─ cancel input ───────────────► IDLE（丢弃本次输入）
  └─ capture error ──────────────► ERROR（旧回答已中断时不可假装仍在播）

PAUSED_OUTPUT
  ├─ resume key/button ──────────► AGENT_SPEAKING
  └─ PTT key-down ───────────────► INTERRUPTING ─► CAPTURING
```

状态机实现应避免仅通过一个 `tts_enabled` 布尔值表达所有情况。建议拆分持久偏好、当前轮生成状态、当前播放状态、输入采集状态。

## 7. 打断时序与数据一致性

按下“打断并说话”时，建议上层按此顺序处理：

1. 记录打断事件、当前 turn id 和触发来源（PTT、语音门槛、停止按钮等）。
2. 在停止/清空播放前读取真实播放进度（已播帧数或时长），不要把已合成/已送入设备的量误当成用户已听到的量。
3. 根据进度截断当前回答上下文，只保留实际播出的文字；把“回答被用户打断”状态写入对话上下文或 turn metadata。
4. 发出本轮取消：LLM stop/cancel token、工具取消、TTS 合成取消、pending TTS 队列清空。
5. 停止或快速淡出音频输出，清理设备缓冲；对无法撤回的声卡尾缓冲使用小缓冲或短淡出控制。
6. 开始/保持麦克风采集，持续将用户音频送入 VAD/ASR；不要因停止扬声器而误停止 capture worker。
7. 松开后等待最终转写/端点，再由现有 `TurnAdmission` 决定是否建立新 turn。

取消是异步的。使用 turn id / generation id 防止旧轮迟到的 token 或音频块在新轮开始后重新进入播放队列。

## 8. 延迟打断策略设计

若后续要支持“说到几个字/一句话后才打断”，可以把策略做成可配置枚举，而不是继续叠加互相覆盖的布尔值：

| 策略 | 触发条件 | 体验/风险 |
|---|---|---|
| `ImmediateOnKeyDown` | 专用 PTT 键按下 | 最快、最确定；按键就是明确意图 |
| `SpeechDuration` | 连续有效语音达到 `min_speech_ms` | 对噪声有去抖；需要等待时间，期间应降低 Agent 音量 |
| `PartialText` | partial ASR 达到最小词/字数 | 能过滤无意义短音；受 ASR 延迟和转写修订影响 |
| `UtteranceEnd` | VAD/语义端点确认一句结束 | 意图最完整；停播最晚，适合非紧急“听完再决定” |
| `Hybrid` | 按键为必要条件，时长/文本/端点为确认条件，任一达到规则触发 | 可平衡误打断与延迟，参数更复杂 |

### 推荐门槛顺序

1. 按键状态是显式用户意图（若采用手动模式）。
2. 音频门控过滤极短噪声（初始值可从现有 `barge_in_min_ms` 周边评估，不直接假设其最优）。
3. 可选 partial transcript 最短长度，中文按字符数，英文按词数；需考虑 ASR partial 会回改。
4. 可选端点确认，用于决定提交 utterance，不应成为“何时停止扬声器”的唯一条件。

建议把“停止扬声器”和“确认用户说完、提交新轮”分开：前者是 barge-in 决策，后者是 turn-taking 决策。这样用户可以先让 Agent 安静下来，再继续组织表达。

## 9. 暂停、静音与取消的内部接口建议

不要把所有动作折叠到 `stop()`。后续可考虑让播放控制层明确暴露类似以下操作（名称仅示意）：

```cpp
enum class PlaybackAction {
    Pause,          // 保留播放位置，可恢复
    Resume,
    Mute,           // 输出音量归零，逻辑播放继续
    Unmute,
    StopPlayback,   // 停播放与待播音频，不必然停止 LLM
    CancelTurn      // 取消 LLM/工具/TTS 当前轮
};
```

关键语义：

- `Pause` 与 `Mute` 的播放游标处理不同。暂停游标不前进；静音时游标随时间前进。
- `StopPlayback` 不等于 `CancelTurn`。停止播放后仍可能需要保留完整文字答案供屏幕阅读。
- `CancelTurn` 必须有 turn identity，确保旧轮取消不会误伤刚启动的新轮。
- 自动播报关闭只决定是否将新回答送入 TTS，不代表静音当前音频或取消当前生成。
- 暂停期间要有队列上限/背压；否则长回答会全部排队，用户恢复后会听到过时语音。
- 若声卡/API不能精确恢复缓冲，应把暂停定义为“暂停逻辑 TTS 段并可从最近安全句界继续”，不能承诺采样级无缝恢复。

## 10. 配置与 UI 建议

### 设置项（后续）

- `interrupt_mode`: `manual_immediate`（默认建议）/ `speech_duration` / `partial_text` / `utterance_end` / `hybrid`
- `interrupt_min_speech_ms`: 最短有效语音门槛
- `interrupt_min_chars_zh`: 中文 partial 最短字符数（若启用）
- `interrupt_min_words_other`: 其他语言 partial 最短词数（若启用）
- `interrupt_duck_volume`: 延迟确认期间 Agent 音量比例
- `playback_pause_queue_limit_ms`: 暂停期间可保留的 TTS 队列上限
- `fade_out_ms`: 打断停止时的淡出时间
- `resume_after_pause`: 暂停后恢复原播报 / 只播最新安全段 / 不恢复

以上应先做用户体验验证，再定默认值。短语音时长不是跨语言、跨麦克风都通用的门槛。

### 控件和提示

- 语音播报 checkbox：表示新回答自动发声偏好。
- 暂停/恢复按钮：只表示当前 playback pause 状态。
- 停止回答按钮：取消当前生成与输出，不自动启动录音。
- PTT 键按住时，状态栏显示“正在听你说（已打断当前回答）”。松开后显示“正在转写”。
- 如果 PTT 用作打断键，应在 tooltip/帮助文本写清“播放期间按下会立即停止当前回答”。
- 全局快捷键重复、焦点在输入框、窗口失焦导致 key-up 丢失、窗口关闭等情况都要有安全释放路径。

## 11. 异常和边界情况

| 情况 | 建议处理 |
|---|---|
| 按下后立即松开 | 取消采集或按现有最短语音规则处理；旧回答已经停止时提示“没有识别到语音”，不要静默伪装为仍在播。 |
| ASR 最终结果为空/失败 | 保留已显示的旧回答文本和被打断标记；允许用户重试。是否续播剩余内容需单独定义，默认不自动续播，避免抢话。 |
| VAD 把 Agent 回声当用户语音 | 先处理 AEC/reference audio 和 VAD 门控；不要仅靠提高时长阈值掩盖回声问题。 |
| 按键松开事件丢失（窗口失焦/系统切换） | 窗口 deactivate、录音设备错误、应用退出时执行幂等 release/stop，避免麦克风持续占用。 |
| 旧 LLM token 在取消后到达 | 通过 turn id/cancel token 丢弃，不允许追加到新回答或 TTS 队列。 |
| 用户只想静音但不打断 | 仅修改输出音量，不触碰当前 turn 的 cancel token 或 ASR 录音状态。 |
| 用户只想停止回答、不说话 | 独立 Stop/Cancel 操作，不启动麦克风。 |
| TTS 句子已经合成但未播放 | 作为 pending 音频清掉；如只暂停则保留但需受队列上限控制。 |

## 12. 分阶段落地建议

### 阶段 0：确定产品语义（当前讨论）

- 确认 PTT 在 Agent 播报期间是否立即打断。
- 确认暂停/静音的差别，以及关闭自动播报的持久化语义。
- 确认空 ASR、误触、取消后是否提供“继续播报”。

### 阶段 1：打断闭环

- 把 PTT key-down 与 Orchestrator 当前 turn 的取消连接起来。
- 在清播放队列前读取播放游标并同步被打断回答的上下文。
- 确保按住期间麦克风继续工作，key-up 按现有流程完成 ASR。
- 用 turn id 丢弃取消后的迟到 token/音频块。
- 清晰显示 listening/transcribing/cancelled 状态。

### 阶段 2：暂停/恢复

- 增加可恢复的 playback pause/resume 控制，不复用 stop。
- 定义暂停期间生成的背压、缓存上限和恢复后的过期内容处理。
- 明确暂停期间用户输入是否关闭；若允许，则按 PTT 立即转打断模式。

### 阶段 3：智能门槛

- 增加手动立即、语音时长、partial 文本、端点确认等策略。
- 在延迟确认阶段可 duck 当前播报，降低回声污染。
- 记录误触、打断延迟、ASR 丢词、回声误触发、用户重说率等指标，再调默认值。

### 阶段 4：质量评估

- 比较 key-down 到播放能量停止的延迟。
- 比较 ASR 的首个稳定 partial 延迟和整句识别率（播放中与停止后分别统计）。
- 评估上下文截断是否保留了确实播出的句子，并移除了未听到部分。
- 检查不同采样率、缓冲大小、SAPI/TTS provider 下暂停/恢复语义是否一致。

## 13. 验收标准建议

打断闭环至少满足：

1. Agent 播报时按下 PTT 后，输出在可接受的设备缓冲时延内停止；不会等到最终 ASR 返回才停。
2. 按住期间用户音频持续送入录音/识别；松开后能完成一次正常转写和轮次准入。
3. 取消后旧轮迟到的 token、TTS 音频不会重新开始播放，也不会写入新轮。
4. 被打断回答的历史只保留实际播出的内容；未播放部分不会被后续模型误认为已告知用户。
5. 关闭自动播报只关闭新回答的自动发声，不会意外取消回答或阻止文本显示。
6. 暂停/恢复与停止/取消有独立状态、独立 UI 反馈和可验证的行为。
7. VAD/ASR 能区分较常见的 Agent 回声；如果当前设备/音频链路无法做到，应在产品层避免承诺“播放期间自然插话可靠可用”。

## 14. 外部技术依据

- [OpenAI Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)：VAD 可配置为在用户开始说话时取消响应；客户端停止当前音频播放，并根据真实已播放时长截断服务端对话项，避免未听到的内容留在上下文中。
- [OpenAI Realtime client events](https://developers.openai.com/api/reference/resources/realtime/client-events)：`conversation.item.truncate` 用于把服务器端音频/文本历史对齐到客户端实际播放位置。
- [Qt QAudioSink](https://doc.qt.io/qt-6/qaudiosink.html)：`suspend()` 暂停并保留缓冲，`resume()` 恢复；`reset()` 立即停止并丢弃缓冲。这说明暂停、恢复和清空播放应是不同操作。实际项目播放端是否基于该类仍需按当前 provider 确认。
- [Microsoft SAPI ISpVoice::Pause](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ms719596%28v%3Dvs.85%29)：SAPI 提供 Pause/Resume 机制；其 pause count 语义意味着调用方需要严格成对管理暂停和恢复。

外部 API 只能说明各类控制在技术上可表达；本项目最终行为仍应由本地 TTS provider、音频设备和 turn orchestration 的实际实现决定。

## 16. 实现现状（2026-10-10）

对照 §12 的分阶段方案，实际落地情况：

| 阶段 | 状态 | 说明 |
|---|---|---|
| 阶段 0 确定产品语义 | ✅ | 采用方案 A（按键/开口即打断）+ duck 确认，见下 |
| 阶段 1 打断闭环 | ✅ | PTT key-down → `begin_capture()` → 播报中立即 `interrupt_agent_()`；停声前取 `played_ratio()` 截断上下文；turn id 丢弃迟到 token |
| 阶段 2 暂停/恢复 | ❌ | `PlaybackAction` 枚举未实现，`AudioRouter` 只有 start/stop，无 pause/resume/mute |
| 阶段 3 智能门槛 | ⚠️ 部分 | 见「打断门槛」小节；duck 与 `barge_in_min_ms` 已生效，但 duck 是固定比例、无背压队列上限 |
| 阶段 4 质量评估 | ⚠️ 部分 | `BargeInLatency` 已埋点，但起点是 VAD 检测时刻而非用户开口，偏乐观 100~300ms；ASR 播放中/停止后分组统计未做 |

### 语音输入方式（设置 → 播报与交互）

两种方式只在"怎么开始录音"上不同，打断规则按各自意图强度区分：

| 方式 | 开始录音 | 打断规则 |
|---|---|---|
| **VAD 自动切分**（默认） | 麦克风常开，VAD 检测到说话自动开始 | 开口后先 duck，持续超过 `min_ms` 才真打断（过滤咳嗽） |
| **手动按键（PTT）** | 按住空格/🎙，松开即转写 | 按下即打断，不等门槛（按键本身就是明确意图） |

对应配置：`agent.yaml` 的 `input_mode: vad | ptt`。界面上的 VAD 芯片与设置页单选按钮是同一个开关。

### 打断门槛（`barge_in` 段）

| 配置项 | 默认 | 作用 |
|---|---|---|
| `min_ms` | 160 | 开口后需持续这么久才算插话，低于则视为噪声不打断 |
| `duck_volume` | 0.35 | 门槛等待期间 Agent 的音量比例，避免盖住用户说话 |
| `require_threshold` | true | 关掉即退回"开口即打断"（咳嗽也会掐掉回答） |
| `fade_out_ms` | 40 | 打断时播报淡出时长，避免硬切爆音 |

### 本轮修掉的实现缺陷

1. **淡出是死代码**：`fading_out_` / `fade_out_start_frame_` / `fade_out_frames_` 从未被赋值，
   打断实际是硬切。现为 `AudioRouter::request_fade_out_stop()`：已播部分丢弃、
   缓冲截断到淡出窗口、淡出期间丢弃新帧（否则"边淡边补"）。
2. **播放回调会把打断后的状态踢回 Idle**：淡出走完会 `enter_idle_()`，
   而此时打断路径已在 Listening —— 用户正在说话的话 mic 直接停。
   已加 `natural_end = (state == Speaking)` 守卫。
3. **`barge_in_min_ms` 是死配置**：`SmartTurn::evaluate_barge_in()` 全仓库零调用点，
   打断退化成硬编码"开口即打断"。现已改为 duck + 计时确认。
4. **GUI 没有把 AppConfig 传进 OrchestratorConfig**：`buildOrchestrator_()` 一直用
   `Orchestrator::Config{}`，`agent.yaml` 的 `eou:` / `barge_in:` 整段都不生效。
5. **PTT 失焦不释放**：按住空格后 Alt+Tab / 锁屏收不到 key-up，麦克风一直占用。
   现补 `changeEvent` / `closeEvent` → 幂等 `releasePtt_()`。
6. **yaml 短 key 回写不安全**：`set_scalar` 全局搜 `key:`，改 `min_ms` 会命中
   `fade_out_ms`。新增 `yaml_edit::set_in_group()` 限定分组体边界。

验证：`tests/test_barge_in_control.cpp`（30+ 断言，覆盖淡出帧数/单调性/末帧幅度、
duck、配置解析、yaml 分组编辑与写入→解析往返），`ctest` 19/19 通过，构建零警告。
